# Contributing to ZMS Labs projects

Use the repository's own contribution instructions when they exist. This is the fallback guidance for projects without a local guide.

1. Read the README, current status, and relevant design or usage documentation. For a fork, check which changes belong here and which belong upstream.
2. Keep the change focused on one problem you can name. For a larger change, open an issue first, where the project has an issue tracker, so the direction is agreed before you spend time on it.
3. Follow the project's existing style, license, attribution and sign-off rules. Sign-off means adding a Signed-off-by line to each commit, for example with `git commit --signoff`, where the project asks for one. Add or update documentation when behavior or usage changes.
4. Run the checks appropriate to the change and state what you verified. Distinguish a local result from a deployed or live-observed outcome.
5. Open a pull request explaining the problem, resulting behavior, verification, and any remaining limitation.

Use made-up examples and minimal reproductions. Do not include credentials, personal information, confidential material, private endpoints, or data you are not authorized to disclose in issues, commits, screenshots, or pull requests.

For documentation changes, use the [documentation standard](https://github.com/ZMS-Labs/.github/blob/main/docs/documentation-standard.md). For new or changed diagrams, screenshots, charts and illustrations, follow the [visual documentation review](https://github.com/ZMS-Labs/.github/blob/main/docs/visual-documentation-review.md): check the rendering at the widths and in the themes the page supports, and use generated artwork only for labeled illustrations, never as evidence or as an exact technical diagram. Repository-specific requirements take precedence over this shared guidance.
